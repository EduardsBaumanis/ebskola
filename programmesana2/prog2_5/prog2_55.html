5.5 Algoritmu efektivitāte

Sasniedzamais rezultāts: Apgūt Big O notation (lielā O notācija) un optimizēt spēles algoritmus.

SR 2.4.19. Algoritmu efektivitāte SR 2.4.5. Datu analīze un vizualizācija

Teorija: algoritmu laika sarežģītība (Big O) un profilēšana

Laika sarežģītība un lielā O notācija (Big O notation)

Viena un tā paša koda izpildes ilgums milisekundēs uz dažādiem datoriem atšķiras, tāpēc algoritmus salīdzina pēc laika sarežģītības (time complexity) jeb lielās O notācijas (Big O notation) — tā parāda, cik strauji pieaug darbību skaits, palielinoties ieejas datu apjomam n. To var salīdzināt ar informācijas meklēšanu: atvērt skapīti ar jau zināmu numuru prasa vienu darbību neatkarīgi no skapīšu skaita (O(1)), izlasīt nesakārtotu sarakstu no augšas līdz apakšai prasa līdz pat n pārbaudēm (O(n)), bet situācijā, kur zālē katrs cilvēks paspiež roku katram citam, 10 reižu lielāks cilvēku skaits rada aptuveni 100 reižu vairāk sarokošanos (O(n²)):

NotācijaPieauguma veidsTipisks piemērs
O(1)KonstantsDirect array access (tieša piekļuve masīva elementam pēc indeksa) vai Dictionary atslēga.
O(log n)LogaritmisksBinary search (binārā meklēšana sakārtotā sarakstā, katrā solī atmetot pusi).
O(n)LineārsIteration (viena cikla pārlase pār visiem n elementiem).
O(n log n)LinearitmisksEfektīva kārtošana: Quicksort (ātrā kārtošana), Mergesort (kārtošana ar sapludināšanu).
O(n²)KvadrātisksNested loops (divi ligzdoti cikli, kur katru elementu salīdzina ar katru).
O(2n)EksponenciālsBrute force search (visu iespējamo kombināciju pilnā pārlase).

Ciklu pieaugums, binārā meklēšana un profilēšana (Profiling)

Praksē lielāko veiktspējas atšķirību rada tas, vai problēmu izdodas atrisināt bez ligzdotiem cikliem vai ar sakārtotu datu struktūru:

// O(1) — konstanta piekļuve neatkarīgi no saraksta garuma n
int pirmais = dati[0];

// O(n) — viens cikls: n pieaugot 10×, darbību skaits pieaug ~10×
for (int i = 0; i < n; i++) { GD.Print(dati[i]); }

// O(n²) — ligzdoti cikli: n pieaugot 10×, darbību skaits pieaug ~100×
for (int i = 0; i < n; i++)
    for (int j = 0; j < n; j++)
        if (dati[i] == dati[j]) { /* pāra salīdzināšana */ }

// O(log n) — binārā meklēšana sakārtotā sarakstā
int BinarySearch(List<int> sakartots, int merkis)
{
    int kreisais = 0, labais = sakartots.Count - 1;
    while (kreisais <= labais)
    {
        int vidus = (kreisais + labais) / 2;
        if (sakartots[vidus] == merkis) return vidus;
        if (sakartots[vidus] < merkis) kreisais = vidus + 1;
        else labais = vidus - 1;
    }
    return -1;
}

Pirms koda pārrakstīšanas praksē vienmēr izmanto profilēšanu (profiling) — reālu izpildes laika mērīšanu ar Godot Debugger -> Profiler vai mikrosekunžu skaitītāju Time.GetTicksUsec(). Tādējādi optimizāciju vērts koncentrēt tieši uz tām metodēm, kuras mērījumos patērē visvairāk procesora laika (piemēram, liekiem aprēķiniem, kas izpildās katrā kadrā), nevis uz kodu, kas izpildās tikai vienreiz programmas sākumā:

ulong sakums = Time.GetTicksUsec();
ApstradatDatus(dati);
ulong ilgumsUsec = Time.GetTicksUsec() - sakums;
GD.Print("Izpildes laiks (μs): ", ilgumsUsec);

1. uzdevums

Izmēri O(n) un O(n²) algoritmu izpildes laiku

Kur strādāt: 1) Mapē Scenes/ izveido scēnu Scenes/Benchmark.tscn (Node sakne Benchmark).
2) Mapē Scripts/ izveido jaunu C# skriptu Scripts/Benchmark.cs un piesaisti to Benchmark mezglam.

Pirmajā solī ar Time.GetTicksUsec() mikrosekunžu precizitātē izmērīsim, kā pieaug izpildes laiks vienkāršam ciklam (O(n)) un diviem ligzdotiem cikliem (O(n²)), palielinot elementu skaitu 10 reizes (no n = 200 uz n = 2000).

  1. Izveido jaunu scēnu (Scene → New Scene → Other Node → Node), pārsauc saknes mezglu par Benchmark un saglabā scēnu kā Scenes/Benchmark.tscn.
  2. Piesaisti Benchmark mezglam jaunu skriptu Scripts/Benchmark.cs un pievieno divas metodes — LinearPass(List<int> data) ar vienu ciklu un QuadraticPass(List<int> data) ar diviem ligzdotiem cikliem: 
    private long LinearPass(List<int> data)
{
    long sum = 0;
    for (int i = 0; i < data.Count; i++)
    {
        sum += data[i];
    }
    return sum;
}

private long QuadraticPass(List<int> data)
{
    long matches = 0;
    for (int i = 0; i < data.Count; i++)
    {
        for (int j = 0; j < data.Count; j++)
        {
            if (data[i] == data[j]) matches++;
        }
    }
    return matches;
}
  3. Tajā pašā Scripts/Benchmark.cs failā pievieno palīgmetodi RunComplexityTest(int n), kas izveido List<int> ar n skaitļiem, izmēra abu metožu izpildes laiku mikrosekundēs ar Time.GetTicksUsec() un izdrukā rezultātu: 
    private void RunComplexityTest(int n)
{
    List<int> data = new(n);
    for (int i = 0; i < n; i++) data.Add(i % 50);

    ulong t0 = Time.GetTicksUsec();
    long linRes = LinearPass(data);
    ulong linearUsec = Time.GetTicksUsec() - t0;

    ulong t1 = Time.GetTicksUsec();
    long quadRes = QuadraticPass(data);
    ulong quadUsec = Time.GetTicksUsec() - t1;

    GD.Print($"[Benchmark n={n}] LinearPass O(n): {linearUsec} μs (sum={linRes}) | QuadraticPass O(n²): {quadUsec} μs (matches={quadRes})");
}
  4. Metodē _Ready() izsauc RunComplexityTest(200); un RunComplexityTest(2000); (10× vairāk elementu).
  5. Nospied Build un palaid Scenes/Benchmark.tscn (F6): salīdzini Output konsolē, cik reižu pieauga `LinearPass` laiks un cik reižu pieauga `QuadraticPass` laiks, kad `n` pieauga 10 reizes.

Gatavs, kad: Output panelī redzami mērījumi pie n = 200 un n = 2000, kur LinearPass laiks pieaug ~10 reizes, bet QuadraticPass — ~100 reizes.

2. uzdevums

Atrodi un izlabo katra kadra O(n²) vājo vietu ar Profiler

Kur strādāt: 1) Failā Scripts/Benchmark.cs pievieno katra kadra simulāciju _Process(double delta) ar slēdzi [Export] public bool UseDictionaryLookup.
2) Mērījumus apskati Godot apakšējā panelī Debugger → Profiler un Debugger → Monitors.

Tipiska kļūda labirinta un darbības spēlēs ir katrā kadrā (_Process) meklēt objektu koordinātas ar ligzdotu ciklu pār sarakstu (O(n²)), nevis izmantot vārdnīcu Dictionary<Vector2I, int> ar O(1) meklēšanu. Izmērīsim šo atšķirību ar Godot Profiler.

  1. Atver failu Scripts/Benchmark.cs un pievieno eksportētos laukus un kolekcijas (skat. pilno kodu sadaļā Pilnie faili salīdzināšanai): 
    [Export] public bool UseDictionaryLookup { get; set; } = false;
[Export] public int ObjectCount { get; set; } = 800;

private readonly List<Vector2I> activeCells = new();
private readonly Dictionary<Vector2I, int> cellLookup = new();
  2. Tajā pašā Scripts/Benchmark.cs failā metodē _Process(double delta) salīdzini divus režīmus, kas katrā kadrā pārbauda ObjectCount šūnas:
    • kad UseDictionaryLookup == false: katrai šūnai ar iekšējo ciklu pārmeklē visu activeCells sarakstu (kopā ObjectCount × ObjectCount darbības kadrā — O(n²));
    • kad UseDictionaryLookup == true: katru šūnu pārbauda vārdnīcā ar cellLookup.ContainsKey(pos) (kopā ObjectCount darbības kadrā — O(n)).
  3. Nospied Build, palaid Scenes/Benchmark.tscn (F6) ar izslēgtu Use Dictionary Lookup (false), Godot apakšējā panelī atver Debugger → Profiler un nospied Start.
  4. Pēc 5–10 sekundēm nospied Stop un apskati rindu Frame Time un Script Functions → _Process: pieraksti kadra apstrādes laiku milisekundēs (`ms`) un `FPS`.
  5. Spēles laikā vai Inspector panelī ieslēdz Use Dictionary Lookup (true) (vai spēles logā nospied taustiņu Space, kas pārslēdz režīmu) un Profiler grafikā vēro, kā kadra laiks strauji nokrītas!

Gatavs, kad: Debugger → Profiler grafikā un Output konsolē ir skaidri redzams kadra laika kritums pēc UseDictionaryLookup = true ieslēgšanas.

3. uzdevums

Pierādi uzlabojumu ar mērījumu tabulu pie dubultas slodzes

Kur strādāt: 1) Inspector panelī pie Benchmark mezgla maini Object Count (800 un 1600) un Use Dictionary Lookup (false un true).
2) Mērījumu tabulu un secinājumus ieraksti projekta saknes failā README.md.

Pārbaudīsim, kā abas pieejas uzvedas, kad objektu skaitu dubulto no 800 uz 1600, un noformēsim pierādījumu tabulu failā README.md.

  1. 1. mērījums (parasta slodze, ObjectCount = 800): palaid Scenes/Benchmark.tscn (F6), pieraksti Output konsolē (vai Debugger → Profiler) redzamo kadra laiku (`μs` vai `ms`) un `FPS` vispirms ar UseDictionaryLookup = false, tad nospied Space un pieraksti rādījumus ar UseDictionaryLookup = true.
  2. 2. mērījums (dubulta slodze, ObjectCount = 1600): Inspector panelī nomaini Object Count uz 1600, palaid scēnu (F6) un pieraksti kadra laiku un `FPS` abos režīmos (false un true).
  3. Projekta saknē atver README.md un aizpildi mērījumu tabulu:

Papildu uzdevums — Salīdzini List.Contains ar BinarySearch un Dictionary pie 10 000 elementiem

Kur strādāt: Pievieno metodi CompareSearchStructures() failā Scripts/Benchmark.cs un izsauc to no _Ready().

Ja pamatdarbs ir gatavs, salīdzini trīs meklēšanas pieejas kolekcijā ar 10 000 elementiem: lineāro meklēšanu list.Contains(target) (O(n)), bināro meklēšanu sakārtotā sarakstā list.BinarySearch(target) (O(log n)) un dict.ContainsKey(target) (O(1)).

  1. Failā Scripts/Benchmark.cs izveido sakārtotu List<int> un Dictionary<int, int> ar skaitļiem no 0 līdz 9999.
  2. Ar Time.GetTicksUsec() izmēri laiku, 1000 reizes meklējot pēdējo elementu 9999 ar list.Contains(9999), list.BinarySearch(9999) un dict.ContainsKey(9999), un izdrukā visus trīs laikus konsolē.

Gatavs, kad: Output konsolē redzams, ka BinarySearch un Dictionary.ContainsKey ir desmitiem reižu ātrāki par List.Contains.

Pilnie faili salīdzināšanai

Fails — Scripts/Benchmark.cs (piesaistīts Scenes/Benchmark.tscn saknes mezglam Benchmark):

using Godot;
using System.Collections.Generic;

public partial class Benchmark : Node
{
    [Export] public bool UseDictionaryLookup { get; set; } = false;
    [Export] public int ObjectCount { get; set; } = 800;

    private readonly List<Vector2I> activeCells = new();
    private readonly Dictionary<Vector2I, int> cellLookup = new();
    private double logTimer = 0.0;
    private int lastCount = -1;

    public override void _Ready()
    {
        // 1. uzdevums: O(n) pret O(n²) pie n = 200 un n = 2000
        RunComplexityTest(200);
        RunComplexityTest(2000);

        RebuildCollections();
    }

    private void RebuildCollections()
    {
        activeCells.Clear();
        cellLookup.Clear();
        for (int i = 0; i < ObjectCount; i++)
        {
            Vector2I pos = new(i % 40, i / 40);
            activeCells.Add(pos);
            cellLookup[pos] = i;
        }
        lastCount = ObjectCount;
    }

    public override void _Process(double delta)
    {
        if (lastCount != ObjectCount)
        {
            RebuildCollections();
        }

        if (Input.IsKeyPressed(Key.Space))
        {
            UseDictionaryLookup = !UseDictionaryLookup;
            GD.Print($"[Benchmark] Režīms pārslēgts: UseDictionaryLookup = {UseDictionaryLookup}");
        }

        ulong t0 = Time.GetTicksUsec();
        int found = 0;

        if (!UseDictionaryLookup)
        {
            // Neoptimizēta O(n²) meklēšana katrā kadrā (divi ligzdoti cikli)
            for (int i = 0; i < activeCells.Count; i++)
            {
                Vector2I target = activeCells[i];
                for (int j = 0; j < activeCells.Count; j++)
                {
                    if (activeCells[j] == target)
                    {
                        found++;
                        break;
                    }
                }
            }
        }
        else
        {
            // Optimizēta O(n) pārbaude, izmantojot O(1) Dictionary atslēgu
            for (int i = 0; i < activeCells.Count; i++)
            {
                Vector2I target = activeCells[i];
                if (cellLookup.ContainsKey(target))
                {
                    found++;
                }
            }
        }

        ulong frameWorkUsec = Time.GetTicksUsec() - t0;

        logTimer += delta;
        if (logTimer >= 1.0)
        {
            logTimer = 0.0;
            string mode = UseDictionaryLookup ? "Dictionary O(n)" : "List ligzdotais O(n²)";
            GD.Print($"[Benchmark N={ObjectCount}] {mode} -> {frameWorkUsec} μs kadrā | FPS: {Engine.GetFramesPerSecond()} (atrasti={found})");
        }
    }

    private void RunComplexityTest(int n)
    {
        List<int> data = new(n);
        for (int i = 0; i < n; i++) data.Add(i % 50);

        ulong t0 = Time.GetTicksUsec();
        long linRes = LinearPass(data);
        ulong linearUsec = Time.GetTicksUsec() - t0;

        ulong t1 = Time.GetTicksUsec();
        long quadRes = QuadraticPass(data);
        ulong quadUsec = Time.GetTicksUsec() - t1;

        GD.Print($"[Benchmark n={n}] LinearPass O(n): {linearUsec} μs (sum={linRes}) | QuadraticPass O(n²): {quadUsec} μs (matches={quadRes})");
    }

    private long LinearPass(List<int> data)
    {
        long sum = 0;
        for (int i = 0; i < data.Count; i++)
        {
            sum += data[i];
        }
        return sum;
    }

    private long QuadraticPass(List<int> data)
    {
        long matches = 0;
        for (int i = 0; i < data.Count; i++)
        {
            for (int j = 0; j < data.Count; j++)
            {
                if (data[i] == data[j]) matches++;
            }
        }
        return matches;
    }
}
Pie n = 2000 kvadrātiskais algoritms ir simtiem reižu lēnāks par lineāro; katra kadra pārbaudē pāreja no ligzdota cikla uz Dictionary samazina kadra apstrādes laiku no vairākām milisekundēm līdz dažām mikrosekundēm.

Ko sagatavo

Stundas mērķis: Tu proti izmērīt koda izpildes laiku ar Time.GetTicksUsec() un Godot Profiler, salīdzināt O(n) un O(n²) pieaugumu un ar skaitļiem pierādīt optimizācijas ieguvumu.

GitHub krātuvē jābūt:

  • Scēnai Scenes/Benchmark.tscn un skriptam Scripts/Benchmark.cs.
  • Ekrānuzņēmumam ar Godot Debugger → Profiler vai Output paneli pirms un pēc optimizācijas ieslēgšanas.
  • Failam README.md ar aizpildītu mērījumu tabulu (gan pie 800, gan pie 1600 objektiem) un secinājumu par O(n) un O(n²) atšķirību.

Kā iesniedz: Veic commit un push (nosūtīšana uz attālo krātuvi). Skolotāja norādītajā vietā ievieto tikai GitHub krātuves saiti; visiem prasītajiem failiem, README.md pierakstiem un pierādījumiem jābūt pašā krātuvē.

Ja kaut kas nestrādā

  • Mēģini optimizēt bez profiling (profilēšanas): 'Premature optimizācija is sakne of all evil' - vienmēr profilē vispirms.
  • O(n²) paslēpts API (lietojumprogrammas saskarne): Some Godot function iekšēji ir O(n) - find_child loop = O(n²).
  • Cache invalidation (kešatmiņas atjaunināšana): Aizmirsis update cache (kešatmiņa) pēc datu izmaiņas - bugs (kļūdas).
