5.5 Algoritmu efektivitāte

Stundas uzdevums: Apgūt Big O notation (lielā O notācija) un optimizēt spēles algoritmus.

SR 2.4.19. Algoritmu efektivitāte SR 2.4.5. Datu analīze un vizualizācija

Teorija: algoritmu laika sarežģītība (Big O) un profilēšana

Laika sarežģītība un lielā O notācija (Big O notation)

Viena un tā paša koda izpildes ilgums milisekundēs uz dažādiem datoriem atšķiras, tāpēc algoritmus salīdzina pēc laika sarežģītības (time complexity) jeb lielās O notācijas (Big O notation) — tā parāda, cik strauji pieaug darbību skaits, palielinoties ieejas datu apjomam n. To var salīdzināt ar informācijas meklēšanu: atvērt skapīti ar jau zināmu numuru prasa vienu darbību neatkarīgi no skapīšu skaita (O(1)), izlasīt nesakārtotu sarakstu no augšas līdz apakšai prasa līdz pat n pārbaudēm (O(n)), bet situācijā, kur zālē katrs cilvēks paspiež roku katram citam, 10 reižu lielāks cilvēku skaits rada aptuveni 100 reižu vairāk sarokošanos (O(n²)):

NotācijaPieauguma veidsTipisks piemērs
O(1)KonstantsDirect array access (tieša piekļuve masīva elementam pēc indeksa) vai Dictionary atslēga.
O(log n)LogaritmisksBinary search (binārā meklēšana sakārtotā sarakstā, katrā solī atmetot pusi).
O(n)LineārsIteration (viena cikla pārlase pār visiem n elementiem).
O(n log n)LinearitmisksEfektīva kārtošana: Quicksort (ātrā kārtošana), Mergesort (kārtošana ar sapludināšanu).
O(n²)KvadrātisksNested loops (divi ligzdoti cikli, kur katru elementu salīdzina ar katru).
O(2n)EksponenciālsBrute force search (visu iespējamo kombināciju pilnā pārlase).

Ciklu pieaugums, binārā meklēšana un profilēšana (Profiling)

Praksē lielāko veiktspējas atšķirību rada tas, vai problēmu izdodas atrisināt bez ligzdotiem cikliem vai ar sakārtotu datu struktūru:

// O(1) — konstanta piekļuve neatkarīgi no saraksta garuma n
int pirmais = dati[0];

// O(n) — viens cikls: n pieaugot 10×, darbību skaits pieaug ~10×
for (int i = 0; i < n; i++) { GD.Print(dati[i]); }

// O(n²) — ligzdoti cikli: n pieaugot 10×, darbību skaits pieaug ~100×
for (int i = 0; i < n; i++)
    for (int j = 0; j < n; j++)
        if (dati[i] == dati[j]) { /* pāra salīdzināšana */ }

// O(log n) — binārā meklēšana sakārtotā sarakstā
int BinarySearch(List<int> sakartots, int merkis)
{
    int kreisais = 0, labais = sakartots.Count - 1;
    while (kreisais <= labais)
    {
        int vidus = (kreisais + labais) / 2;
        if (sakartots[vidus] == merkis) return vidus;
        if (sakartots[vidus] < merkis) kreisais = vidus + 1;
        else labais = vidus - 1;
    }
    return -1;
}

Pirms koda pārrakstīšanas praksē vienmēr izmanto profilēšanu (profiling) — reālu izpildes laika mērīšanu ar Godot Debugger -> Profiler vai mikrosekunžu skaitītāju Time.GetTicksUsec(). Tādējādi optimizāciju vērts koncentrēt tieši uz tām metodēm, kuras mērījumos patērē visvairāk procesora laika (piemēram, liekiem aprēķiniem, kas izpildās katrā kadrā), nevis uz kodu, kas izpildās tikai vienreiz programmas sākumā:

ulong sakums = Time.GetTicksUsec();
ApstradatDatus(dati);
ulong ilgumsUsec = Time.GetTicksUsec() - sakums;
GD.Print("Izpildes laiks (μs): ", ilgumsUsec);

Papildu uzdevums - Salīdzini List (saraksts) ar Dictionary (vārdnīca) meklēšanu

Kur strādāt: Abu struktūru meklēšanas metodes un to mērījumus pievieno Scripts/Benchmark.cs; izsauc tos no _Ready().

Ja pamatdarbs ir gatavs, izmēri data structure (datu struktūru) atšķirību.

  1. Izveido List<int> ar 10000 elementiem.
  2. Izveido Dictionary<int, int> ar tiem pašiem datiem.
  3. Izmēri laiku, meklējot pēdējo elementu abās struktūrās.
  4. Izdrukā abus laikus.
  5. Pieraksti, kura struktūra bija ātrāka un par cik reizēm.

Gatavs, kad: meklēšana Dictionary ir manāmi ātrāka nekā loop pār List.

Paplašināts koda piemērs 
using Godot;
using System.Collections.Generic;

// Spatial hash priekš ātras kolīzijas
public class SpatialHash
{
    private const int CellSize = 64;
    private readonly Dictionary<long, List<Node2D>> grid = new();

    private long CellKey(int cx, int cy)
    {
        return ((long)cx << 32) | (uint)cy;
    }

    public void Rebuild(IEnumerable<Node2D> objects)
    {
        grid.Clear();
        foreach (Node2D obj in objects)
        {
            Vector2 pos = obj.Position;
            int cx = (int)(pos.X / CellSize);
            int cy = (int)(pos.Y / CellSize);
            long key = CellKey(cx, cy);
            if (!grid.ContainsKey(key)) grid[key] = new List<Node2D>();
            grid[key].Add(obj);
        }
    }

    public List<Node2D> GetNearby(Vector2 pos)
    {
        int cx = (int)(pos.X / CellSize);
        int cy = (int)(pos.Y / CellSize);
        List<Node2D> result = new();
        for (int dx = -1; dx <= 1; dx++)
        {
            for (int dy = -1; dy <= 1; dy++)
            {
                if (grid.TryGetValue(CellKey(cx + dx, cy + dy), out List<Node2D> cell))
                {
                    result.AddRange(cell);
                }
            }
        }
        return result;
    }
}
1000 objektu kolīzijas pārbaude: bez optimizācijas - 5 ms, ar spatial hash (jaucējvērtība) - 0.3 ms.

Ko sagatavo

Stundas mērķis: Tu proti izmērīt koda izpildes laiku, atrast lēnāko vietu ar Godot profiler, to izlabot un ar skaitļiem pierādīt, ka uzlabojums tiešām notika.

GitHub krātuvē jābūt:

  • Tabula ar FPS un profiler laiku pirms un pēc labojuma, arī ar dubultu slodzi.
  • Ekrānuzņēmums ar Godot profiler pirms labojuma un pēc tā.
  • Commit ziņa, kurā aprakstīts, ko tieši optimizēji.
  • README.md: kura function bija O(n) un kura O(n kvadrātā) un kā tu to noteici.

Kā iesniedz: Veic commit un push (nosūtīšana uz attālo krātuvi). Skolotāja norādītajā vietā ievieto tikai GitHub krātuves saiti; visiem prasītajiem failiem, README.md pierakstiem un pierādījumiem jābūt pašā krātuvē.

Ja kaut kas nestrādā

  • Mēģini optimizēt bez profiling (profilēšanas): 'Premature optimizācija is sakne of all evil' - vienmēr profilē vispirms.
  • O(n²) paslēpts API (lietojumprogrammas saskarne): Some Godot function iekšēji ir O(n) - find_child loop = O(n²).
  • Cache invalidation (kešatmiņas atjaunināšana): Aizmirsis update cache (kešatmiņa) pēc datu izmaiņas - bugs (kļūdas).
