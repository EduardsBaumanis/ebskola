# 02 špikeris

10. tēmas špikeris - projektēšana un plānošana

Problēmas formulēšana, prasības, datu modelis, prezentācija un plāns. Šajā tēmā kodu neraksta - te top dokumenti.

10.1 Problēmas formulējums

## Vājš formulējums (tā raksta lielākā daļa)
Spēli ir grūti papildināt un tas aizņem daudz laika.

  Kas nav labi:
  - "grūti" un "daudz" nav skaitļi - to nevar pārbaudīt
  - nav pateikts, KAS tieši ir grūti
  - nav skaidrs, kad problēma būtu atrisināta

## Spēcīgs formulējums
Pēc katra koda labojuma jāizspēlē vismaz 8 partijas, lai pārbaudītu
visas uzvaras līnijas. Tas aizņem ~15 minūtes. Nedēļā labojumu ir ~6,
tātad 1,5 stundas nedēļā aiziet pārbaudēm, un 3 no 10 reizēm kļūda
paliek nepamanīta.

  Kas ir labi:
  - skaitļi: 8 partijas, 15 min, 1,5 h, 3 no 10
  - konkrēta darbība: pārbaude pēc koda labojuma
  - NAV minēts risinājums - tikai problēma

Risinājumu ("uzrakstīšu testus") šeit nerakstām. Vispirms problēma, tikai tad risinājums.

10.2 Lietotāju stāsti un akceptēšanas kritēriji

## User Story
Kā [lietotājs], es vēlos [darbība], lai [ieguvums].

Kā spēlētājs, es vēlos, lai spēle pati paziņo uzvarētāju,
lai nav jāskaita zīmes pašam.

## Akceptēšanas kritēriji - PĀRBAUDĀMI
- [ ] Trīs vienādas zīmes rindā, kolonnā vai diagonālē -> "Uzvar X/O"
- [ ] Pilns laukums bez uzvarētāja -> "Neizšķirts"
- [ ] Kamēr uzvarētāja nav, spēle prasa nākamo gājienu
      -> uz katru var atbildēt tikai JĀ vai NĒ (10.4: katrs kļūst par testu)

## NEPĀRBAUDĀMI - tā nevajag
- [ ] Paziņojums izskatās labi       <- kā izmērīt?
- [ ] Spēle strādā ātri              <- cik ātri?

## Prioritāte
M = obligāts , V = vēlams , apjoms 1-5
Sāc ar to, kas ir M un ar mazāko apjomu.

Ja kritēriju nevar pārbaudīt ar jā/nē, tas noved pie strīda par to, vai darbs ir gatavs.

10.3 Datu modelis un UI plūsma

ER diagramma - kādi dati sistēmā vispār ir

  ┌───────────────┐             ┌──────────────────────┐
  │  Spēlētājs    │  piedalās   │  Spēle               │
  ├───────────────┤────────────►├──────────────────────┤
  │ vards         │             │ id (atslēga)         │
  │ zime (X/O)    │             │ laukums              │
  │ uzvaras       │             │ pasreizejais_gajiens │
  └───────────────┘             └──────────────────────┘

UI plūsma - pa kādiem ekrāniem lietotājs staigā

  [Sākums] --nospiež Sākt--> [Spēle] --uzvar--> [Rezultāts]
      ▲                                              │
      └───────────── Spēlēt vēlreiz ─────────────────┘

Pārbaude:
  - vai katram ER atribūtam ir ekrāns, kur to redz?
  - vai no katra ekrāna var tikt PROM? (nav strupceļu)

Zīmē abas diagrammas kopā - tikai tā pamanīsi datus, ko neviens ekrāns nerāda.

10.4 Testēšana ar unittest

import unittest
from spele_104 import uzvaretajs      # fails blakus: tema10/spele_104.py


class TestUzvaretajs(unittest.TestCase):

    def test_x_augseja_rinda(self):  # nosaukums sākas ar test_
        laukums = [["X", "X", "X"],
                   ["O", "O", ""],
                   ["", "", ""]]
        self.assertEqual(uzvaretajs(laukums), "X")


unittest.main()

# Izvade:  .  /  Ran 1 test  /  OK
# Kļūda:   F  /  AssertionError: None != 'X'  /  FAILED (failures=1)

Viens akceptēšanas kritērijs = viens tests. Ja tests neizdodas, rindā FAIL redzi tā nosaukumu, bet rindā AssertionError — ko funkcija atgrieza un ko tu gaidīji.

10.5 Plāns, resursi un Definition of Done

## Starprezultāti
1. Laukums un gājieni - gatavs, kad divi spēlētāji pēc kārtas ieliek X un O
2. Uzvarētāja pārbaude - gatavs, kad visi testi failā test_104.py iziet (OK)
3. Spēles cikls - gatavs, kad spēle beidzas ar uzvaru vai neizšķirtu
   -> katram pabeigtību var pārbaudīt ar JĀ/NĒ

## Resursi
- Tehniskie: Python 3.12, unittest, VS Code
- Informatīvie: dokumentācija, 3. un 4. tēmas koda paraugi
- Laiks: 3 h nedēļā
- * TRŪKST: piekļuve skolas serverim -> prasīšu skolotājam

## Riski
| Risks | Plāns B |
|---|---|
| Uzvaras pārbaude nepamana diagonāli | tests test_x_diagonale to atklāj |
| Nepaspēju 3. posmu | iesniedzu ar 2 posmiem, 3. kā papildu |

## Definition of Done
- [ ] Visi testi failā test_104.py iziet (OK)
- [ ] Programma palaižas bez kļūdām
- [ ] README apraksta palaišanu
- [ ] Iztestēts ar tukšu un bojātu ievadi

Aizstāvēšanā katrai tehniskai izvēlei jābūt pamatojumam, kas atsaucas uz prasību - nevis "tā bija vieglāk".

10.6 Aizstāvēšanas runa (pitch)

Lifta runa - 45-60 sekundes, 4-5 teikumi:
  1. Āķis      - kas piesaista uzmanību
  2. Problēma  - no 10.1 formulējuma, ar skaitli
  3. Risinājums- ko tu būvē
  4. Ieguvums  - kas mainīsies lietotājam

Slaidu plāns - 5 slaidi, katram VIENA doma:
  1. Āķis          2. Problēma      3. Risinājums
  4. Demo          5. Nākamie soļi

Likumi:
  - ne vairāk par 20 vārdiem uz slaida
  - visi 5 slaidi kopā < 100 vārdi
  - iztestē ar taimeri UN ar klasesbiedru
  - sagatavo atbildes uz 3 jautājumiem, tostarp par risku

Ja klasesbiedrs pēc runas nesaprot, ko tu būvē, vaina ir runā, nevis klausītājā.
